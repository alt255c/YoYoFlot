# Запуск полного backend на исходном датасете

## Основной путь

Из Git-клона или полной поставки исходного кода:

```bash
./build_and_run.sh
```

Команда работает из любой текущей папки. Она создаёт окружение в `.venv`,
устанавливает `requirements.txt` и пакет проекта, проверяет зависимости,
получает исходные данные и строит результат. Веб-сервер не запускается.
Загрузчик поддерживает обычное подтверждение Google Drive для большого файла.
Размер и SHA-256 оригинального архива и семи членов закреплены в
`scripts/dataset_manifest.json`. При несовпадении сборка останавливается;
новая версия источника требует отдельной проверки и обновления манифеста.

```bash
./build_and_run.sh --archive /absolute/path/Airlines-All.zip
./build_and_run.sh --python python3.12 --memory-limit 1GB
./build_and_run.sh --output artifacts/run-02 --report-output artifacts/run-02-report
```

Относительные пути в параметрах считаются от папки вызова. `--data-dir`
задаёт каталог оригиналов, `--work-dir` — промежуточные данные и кэш,
`--output` — неизменяемый снимок продукта. Каталоги не должны пересекаться.
Зависимости для первого запуска требуют доступа к пакетам даже при `--archive`.

## Объём данных и ресурсы

Размеры семи исходных файлов сверены с `scripts/dataset_manifest.json`;
число страниц прочитано из оригинального PDF.

| Вход | Объём |
| --- | --- |
| Оригинальный `Airlines-All.zip` | 477 710 849 байт, около 478 МБ |
| Семь файлов после распаковки внешнего архива | 1 541 640 375 байт, около 1,54 ГБ / 1,44 ГиБ |
| `Skyteam_Timetable.pdf` | 27 514 страниц |

Для полного конвейера планируйте **не менее 50 ГБ свободного дискового места**
и **8 ГБ оперативной памяти или больше**. Это консервативная рекомендация
для подготовки, а не измеренный максимум и не гарантия достаточности для
любых настроек. Помимо оригиналов сохраняются разобранные строки, канонические
таблицы, промежуточные данные, временные файлы DuckDB и итоговые снимки.
Вложенный архив посадочных талонов также обрабатывается полностью.

Значение `--memory-limit 1GB` по умолчанию ограничивает только DuckDB.
Парсеры PDF/XLSX, Python и обучение модели потребляют память дополнительно;
уменьшение этого параметра не задаёт общий предел памяти процесса.

Первый полный прогон требует существенного времени, в том числе для всех
27 514 страниц PDF. Проверенной оценки полного времени здесь нет: она
зависит от оборудования, диска и уже готовых этапов. Следите за сообщениями
прогресса. Для продолжения после прерывания сохраните `--work-dir`
(по умолчанию `data/work/source-product`) и повторите исходную команду:
проверенные совместимые результаты завершённых этапов будут переиспользованы.
Не удаляйте рабочий каталог, если хотите сохранить эту возможность.

## Этапы и результат

1. Проверка/скачивание оригинального ZIP и безопасная атомарная распаковка.
2. Чтение CSV, JSON, XML, fixed-width, YAML, XLSX и PDF без ограничения строк.
3. T12: канонические таблицы; T11: справочник аэропортов и расписания;
   T13: идентичности и различимые сегменты; T14: структурное качество.
4. Факторы M01–M03, пороги исходной калибровочной выборки и основной топ.
5. Граф наблюдаемых совместных событий, IF на полных признаках, чувствительность.
6. Независимый числовой аудит и экспорт CSV/JSON/Markdown для всех людей топа.

По умолчанию результат находится в `artifacts/source-product-report`, проверка
— `artifacts/source-product-verification.json`. Формат описан в
[result_format.md](result_format.md). Сырые CSV для Excel защищены от исполнения
формул; `profiles.json` сохраняет исходные значения без такого представительного
экранирования. Неизвестные даты/координаты не удаляются из списка поездок.

## Повторный запуск и восстановление

Завершённый совместимый снимок проверяется по SHA-256 и переиспользуется.
Прерванные этапы возобновляются из того же `--work-dir`, с проверкой зависимостей.
Не редактируйте файлы внутри снимка. Для новой версии аналитики используйте новый
`--output`; данные core повторно рассчитываются только при изменении их входов,
настроек или реализации core. Лимит DuckDB не является пределом суммарного RSS.

Если готовый raw core перенесён в другой каталог, его можно указать явно:

```bash
./build_and_run.sh --archive /absolute/path/Airlines-All.zip \
  --core-snapshot /absolute/path/to/core \
  --output artifacts/product-new --report-output artifacts/product-new-report
```

Этот режим проверяет все файлы снимка, исходные семь файлов, текущие конфигурации
и справочники. Перед допуском в продукт XLSX coverage сверяется с source report
и canonical locators. Для исправленной ревизии дополнительно обязательна полная
история ремонта. Несовместимый или неполный снимок отвергается; отключения этих
проверок нет. Это переиспользование готового core, а не повторное чтение всех raw.

Исправление вспомогательного coverage выпускается отдельной ревизией: старый
core не переписывается. Утилита `scripts/repair_workbook_coverage.py` принимает
старый core, результат отдельного повторного XLSX ingestion и оригинальный ZIP.
Она требует совпадения всех шести Parquet-хешей с исходными canonical inputs,
неизменных raw, reader, зависимостей и параметров, а также полного списка книг
и листов. Новый core сохраняет исходный source report и остальные данные,
добавляя `repair_manifest.json` и проверочные материалы. Это узкая процедура
восстановления доказанной ошибки coverage, не обычный шаг запуска.

Ошибки чтения или неполное покрытие по умолчанию останавливают полный конвейер.
Скрипт не включает `--allow-source-errors` и не заменяет недоступные источники.
Ограничения исходных данных и предыдущих этапов сохраняются в происхождении.

Семантическая проверка XLSX coverage выполняется при допуске в продукт и в
`--core-snapshot`. Отдельный внутренний запуск T16 не следует считать
прошедшим этот дополнительный gate без проверки продукта.

Отдельные команды после успешной установки:

```bash
.venv/bin/python -m yoyoflot train --input artifacts/core/<core-run-id> --output artifacts/model-02
.venv/bin/python scripts/verify_source_product.py --product artifacts/model-02 --report artifacts/model-02-verification.json
.venv/bin/python -m yoyoflot report --product artifacts/model-02 --output artifacts/model-02-report
```

Полный путь с raw предпочтителен для приёмки. Старые поставленные LFS-таблицы
T13 всё ещё принимаются по закреплённым хешам, но без утверждения о проверенном
raw-прогоне. Для свежего T13 требуются полный манифест и отчёты подготовки.

## Разработка

```bash
.venv/bin/python -m pytest -q
```

Тестовые минимальные примеры проверяют формулы и граничные случаи. Они никогда
не становятся входами конечного продукта. Исторический протокол старой ветки
`docs/validation/source_product.json` не является результатом нового полного
прогона. Текущий протокол публикуется отдельно по фактически выполненным шагам.
