# Маркеры 2.0: сохранённая база, документный конфликт и слабые признаки

Дата: 20.10.2026. Основание: сохранить исходные частоту перелётов, быстрые
возвраты и повторяемость маршрутов без изменения формул, порогов и весов;
добавить документный конфликт и перечисленные пользователем слабые признаки.
[План перехода T32](../tasks/T32.md).

Статус: спецификация и аудит выполнены. Текущий продукт 1.1 продолжает считать
M01–M03; приведённые ниже правила будут подключены при выполнении пунктов 2–6.
[Конфигурация-проект](../configs/markers_v2.yaml) содержит `runtime_enabled: false`.

## Что подтверждено проверкой

В доступных canonical Parquet 310 904 документные строки:

| Источник | Строк | Различных значений документа |
|---|---:|---:|
| BoardingData.csv | 155 147 | 73 263 |
| Sirena-export-fixed.tab | 155 757 | 83 217 |

Полный поиск по `identifier_namespace + value_normalized` обнаружил в каждом
из этих источников один номер с несколькими известными датами рождения:
`8248 013778`. Номер объединяет явно несовместимые пары фамилии и имени.
Сокращение отчества у Глебова отдельной личностью не считается.

| Источник и физическая строка | Имя в оригинале | Дата рождения ISO | Вылет |
|---|---|---|---|
| CSV:83249 | GLEBOV GORDEI M. | 1982-12-31 | 2017-03-09 |
| CSV:92877 | GLEBOV GORDEI M. | 1982-12-31 | 2017-01-16 |
| CSV:134535 | GLEBOV GORDEI MAKAREVICH | 1982-12-31 | 2017-03-10 |
| CSV:150154 | BUROV RAMIL ALBERTOVICH | 1995-08-24 | 2017-01-03 |
| Sirena:93154 | ГЛЕБОВ ГОРДЕЙ МАКАРЕВИЧ | 1982-12-31 | 2017-01-16 |
| Sirena:150694 | БУРОВ РАМИЛЬ АЛЬБЕРТОВИЧ | 1995-08-24 | 2017-01-03 |

Для CSV дата `12/31/1982` разбирается как `%m/%d/%Y`; в Sirena дата уже ISO.
Шесть строк сравнены с соответствующими членами оригинального
`data/Airlines-All.zip`. Хеш архива и хеши файлов совпали с
`scripts/dataset_manifest.json`.

Распакованный локальный Sirena имеет окончания строк CRLF и другой SHA-256.
Его вариант с LF совпадает с закреплённым хешем оригинала; аудит использует
непосредственно оригинальный член ZIP и не меняет распакованный файл.

Две пары CSV/Sirena повторяют одни и те же билет, рейс и время вылета:
`2082229451418171 / SU1057 / 2017-01-16T01:45` и
`7230123462656045 / SU1273 / 2017-01-03T11:15`.
Поэтому утверждение «два независимых источника подтверждают нарушение»
снимается. Наблюдаются шесть строк и четыре описания поездки после схлопывания
двух указанных пар; пространства имён источников остаются разными.
Независимость сбора данных не установлена.

Результат: один пакет проверки с двумя внутристочниковыми конфликтами.
Проверяемое утверждение — противоречие документных данных. Из него нельзя
определить, кто владеет номером, допущена ли опечатка, имеется ли подлог и
имеет ли кто-либо отношение к шпионажу.

## D01 / document_identity_conflict

Название для карточки: **Конфликт паспортного документа**.
Исходное поле имеет тип `document`; тип и орган выдачи документа не угадываются.
Единица первичного результата — `conflict_id`, привязанный к точному номеру
в конкретном `identifier_namespace`. Он содержит участников и свидетельства;
конфликтующие наблюдения не объединяются в единую личность.

Условия положительного значения:

1. Есть точное непустое строковое значение документа в одном пространстве
   имён. Ведущие нули, буквы и внутренние символы не отбрасываются.
2. Есть минимум две разные корректные полные даты рождения.
3. Вместе с различием дат есть несовместимые фамилии **и** имена. Инициал,
   сокращение отчества, порядок токенов или обычная транслитерация сами по
   себе условия не выполняют. Правила сравнения имён версионируются и
   сохраняются рядом с результатом; неоднозначное сравнение остаётся кандидатом.
4. Сохранены `source_id`, `source_record_id`, `observation_id`, `identifier_id`,
   локатор, исходное значение и нормализованное значение каждого свидетельства.
5. При показе результата у профиля существует точная проверяемая связь с его
   наблюдением. Сходство имени и найденный по имени паспорт такой связью не
   являются. Непривязанные строки остаются в пакете проверки с явным статусом.

`matched`: все условия выполнены. `not_matched`: пригодные документные
записи проверены, конфликта в просмотренном наборе нет. `unavailable`: нет
необходимого номера, дат, сравнимых имён или проверяемой связи со свидетельством.
Последнее состояние не подменяется отрицательным результатом.

Отсутствие точной идентичности человека не удаляет **сам конфликт**: пакет
проверки существует на уровне наблюдений. При выводе у человека карточка
показывает роль «связанная запись», сохраняя `identity_status=ambiguous`.
Так конфликт доступен оператору без автоматического слияния двух людей.

## Вес и формула

| Группа | Вес в целевой версии | Основание |
|---|---:|---|
| D01 — конфликт паспортного документа | **20.0** | Новый сильный сигнал с проверяемым противоречием |
| M01 — частота перелётов | **1.0** | Исходный маркер, сохраняется как есть |
| M02 — быстрые возвраты | **1.5** | Исходный маркер, сохраняется как есть |
| M03 — повторяемость маршрутов | **1.0** | Исходный маркер, сохраняется как есть |
| L01 — общая карта лояльности | **0.01** | Новый слабый признак |
| P01 — общий PNR | **0.01** | Новый слабый признак |
| M07 — совместные перелёты | **0.01** | Новый слабый признак |
| D02 — несколько документов у одного имени | **0.01** | Новый слабый признак |
| N01 — ошибка в одной букве имени | **0.01** | Новый слабый признак |
| B01 — отсутствие посадки | **0.01** | Включён в конфигурацию; недоступен на текущих данных |
| M04–M06 — всплески, цепочки, редкость | **0.0, отключены** | Не входят в уточнённый список пользователя |

Повторные пункты «частые перелёты», «быстрые возвраты», «повторяемость
маршрута» соответствуют M01, M02, M03. Их прежние веса сохранены; вторая
копия с малым весом не создаётся. Итого 10 различных критериев: 3 исходных,
1 сильный новый и 6 слабых новых.

Для D01 `value ∈ {0,1}`, `threshold=1`,
`contribution = weight × value` при доступном факторе.
Для недоступного фактора `value=null`, `contribution=0`, причина сохраняется.
Группа D01 даёт максимум один сильный голос и 20 баллов на профиль.
Повторы строк, число файлов, число билетов и два написания имени балл не
умножают. Несколько конфликтных номеров раскрываются списком, группа остаётся
одной.

Для M01–M03 сохраняются прежние веса и существующий множитель выраженности:
`contribution = weight × min(3, value / threshold)` при срабатывании и
доступном факторе. Максимальные вклады: M01 — 3, M02 — 4.5, M03 — 3.
Все три вместе дают максимум **10.5**, как в прежнем расчёте.
Шесть новых слабых критериев бинарные: `contribution = 0.01 × value` при
доступном факторе. Вместе они дают максимум **0.06**. Недоступный фактор
получает `value=null`, вклад 0 и явную причину; его вес в конфигурации
остаётся ненулевым. D01=20 выше максимума 10.56 остальных факторов вместе.

Новый порядок: `strong_matched_group_count DESC`,
`baseline_matched_group_count DESC`, `rule_score DESC`, `person_id ASC`.
Сначала приоритет документного конфликта. Внутри одинакового сильного
приоритета сохраняется прежний первый ключ — число сработавших M01–M03.
Малые новые признаки участвуют в сумме баллов, не увеличивая число базовых
или сильных групп. Поэтому несколько слабых флагов не обходят D01 и не
подменяют исходные три маркера. Общее число срабатываний API отдаёт отдельно.

Новые веса — явная политика приоритета проверки. Вес D01 выбран выше
математического максимума исходной базы и всех новых слабых признаков;
вес 0.01 задаёт только малую поправку. Исходное соотношение весов M01–M03
сохраняется. Размеченных нарушений для статистической подгонки весов нет.
Проценты вероятности и измеренная точность из баллов не вычисляются.

Формулы трёх сохранённых признаков, условия достаточности данных и способы
получения порогов не меняются. При тех же входах и окне должны совпасть
прежние пороги, значения и вклады. В текущем `rules.json`: M01 —
2.2131147540983607, M02 — 0.07142857142857142, M03 — 0.09999999999999998.
Проверенные пороги и состав калибровки фиксируются в новом `rules.json`;
смена входов или окна требует отдельного пересчёта и сохранения новых референсов.
Отключённые критерии не входят в число доступных/сработавших факторов.

IF сохраняется как отдельный эксперимент на `trip_rate_30_days`,
`quick_return_share`, `repeated_route_share` с прежними требованиями полноты.
Он пересобирается вместе с новым продуктом. D01 не добавляется к его входам,
а score IF не меняет основной рейтинг и не добавляет ещё один голос.

## Условия новых слабых признаков

Эти условия описывают будущий расчёт пункта 2 T32. Документный аудит пункта 1
не заявляет, что остальные признаки уже вычислены или проверены на всех строках.

| ID | Условие | Ограничение |
|---|---|---|
| L01 | Одинаковые программа и точный номер карты у разных исходных профилей | Семейное использование и ошибка источника допустимы; личности по карте не сливаются |
| P01 | Точный PNR в одном контексте брони, разные пассажирские записи и совпадающее разрешённое событие рейса | Повтор короткого кода через месяцы на несвязанных рейсах остаётся кандидатом качества данных, не создаёт групповую поездку |
| M07 | Две разные проверенно связанные записи профилей относятся к одному разрешённому событию рейса | Дата и номер рейса сами по себе недостаточны; бронь не объявляется фактической посадкой; повторы источников не умножают вклад |
| D02 | Минимум два точных номера документа у сравнимого имени, известные даты рождения не противоречат друг другу | Однофамильцы не объединяются по имени; неоднозначное владение остаётся кандидатом без начисления конкретному профилю |
| N01 | После нормализации имена отличаются ровно одним буквенным изменением; есть проверенная связь идентичности | Инициалы, транслитерация и перестановки не считаются ошибкой в одной букве; нечёткое имя не присоединяет чужой паспорт |
| B01 | Проверенная связь пассажира с событием и явный пассажирский статус `NO_SHOW` | В текущих данных такого статуса нет: `unavailable`, вклад 0 при весе 0.01. Отсутствие boarding-записи и `LANDED` не подходят |

Для каждого фактора источник, локатор и причина доступны в карточке.
Недоступность не маскируется состоянием `not_matched`; неподтверждённые
поля и несуществующие статусы не генерируются.

## Что требуется от Parquet и API

| Таблица | Назначение и ключ |
|---|---|
| document_conflicts.parquet | Конфликт внутри namespace; `conflict_id`, версия правила, номер, статус и причина |
| conflict_members.parquet | `conflict_id + observation_id`, точный `person_id` при наличии, способ и статус связи |
| marker_evidence.parquet | Свидетельства D01 и шести новых слабых факторов: оригинальные идентификаторы/локаторы, значения, повтор события и происхождение |
| marker_coverage.parquet | `person_id + criterion_id`, доступность всех 10 критериев, число пригодных наблюдений и причина |
| features/explanations/rankings/top50 | Результаты новой версии; типы и величины фиксируются в контракте продукта 2.0 |

Участники конфликта могут находиться среди `ambiguous`. В старом продукте
четыре найденных по точным якорям профиля уже имеют `insufficient_data`.
Условие старого `_features` об обязательной `accepted`-идентичности нельзя
перенести на доступность **наблюдаемого противоречия**. При этом неоднозначный
профиль не становится достоверно установленной физической личностью.

Две строки Sirena пока не имеют точных anchor-связей с текущим snapshot.
Пункт 2 T32 должен использовать полный проверенный `person_links` либо
оставить эти строки непривязанными. Текущее дополнение паспортов по имени в
`ProductStore._document_observation_ids` нельзя использовать для начисления
баллов; пункт 5 заменит его проверенными связями для карточки.

Топ профилей имеет фактический размер. Один пакет конфликта и четыре якорных
профиля не означают четыре независимых нарушения. В представлении конфликтов
пакет отображается единожды со всеми связанными записями; в списке профилей
каждый участник ссылается на тот же пакет. Отдельно считаются профили и
уникальные конфликты. Профили с M01–M03 сохраняются после пересчёта новых
баллов и порядка; старые ранги и количество 5 346 не копируются как готовый
результат новой модели.

## Воспроизведение и границы аудита

```powershell
.venv\Scripts\python.exe scripts\audit_marker_baseline.py
```

[JSON с результатами](validation/t32_marker_baseline.json) содержит хеши
прочитанных файлов, полные локаторы, результаты шести сравнений с оригиналом,
повторные события и точные связи с текущими профилями/сегментами. Хеши входов
до/после исполнения совпадают. Отчёт также фиксирует общий статус canonical
`complete_with_errors` и `pending_real_data_review`; эти ограничения переходят
в дальнейшую проверку происхождения. Человеческая предметная приёмка и
оценка точности этим техническим аудитом не заявляются.
