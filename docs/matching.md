# T13: личности и свидетельства поездок

Пакет 0.6.1, правила resolution:1.0, отдельный контракт resolution 1.0.
Реализация проверена фикстурами и искусственным нагрузочным набором. Полные
реальные таблицы T12/T11 в этой среде отсутствуют; отчёты пользователя не заменяют
прогон T13 и независимую проверку Кириллом. Глобальная точность не заявляется.

## Запуск

Из корня проекта после завершения T12 и исправленного T11:

```powershell
python scripts/run_t13.py --require-all
python scripts/run_t13.py --require-all -q
```

Поддерживаются PyCharm Run и CLI `python -m yoyoflot resolve`. Вход и выход
по умолчанию data/processed, конфиг configs/resolution.yaml, выборка data/review.
Вход — плоский каталог с observations, identifiers, travel_observations,
travel_geography, canonical_report, geography_report и двумя manifest.
Перезапуск readers, T12 или T11 при неизменных входах для T13 не требуется.
`--require-all` проверяет фактическое наличие наблюдений всех шести источников;
без флага допустимы промежуточные наборы и фикстуры.

Обычный запуск показывает этапы, каждые 30 секунд — состояние активного этапа,
затем итог. При известном числе пар/строк показываются счётчик и оценка времени
только этого этапа. На SQL-проверках показывается прошедшее время без ложного
процента готовности. Итог сохраняется в resolution_summary.txt. Успешный `-q`
не печатает ничего; ошибки идут в stderr с кодом 1, Ctrl+C — код 130.
`complete` означает технически завершённую сборку. Приёмка и ревью указаны
отдельно; неоднозначные связи не превращаются в ошибки программы.

## Проверка входа и производительность

Перед чтением и перед публикацией проверяются SHA-256 нужных входов и конфигурации.
Сначала используются canonical_manifest и t11_manifest; T13 читает только три
канонические таблицы, travel_geography и два отчёта. Файлы schedules,
schedule_links и большой provenance для сопоставления не требуются: ID и
source_id/source_record_id/locator уже есть в исходных строках. Полный путь к
reader provenance сохраняется через observation_id/identifier_id/travel_id.

Требуются canonical_contract_version=1.0 и geography_contract_version=1.0.
Таблица T11 должна быть собрана именно из выбранного канонического файла
travel_observations: проверяются входной хеш в geography_report, ключи и сохранённые
базовые значения. Старый T11 на reader-выходах вместо T12 отклоняется. Проверяются
типы, уникальность ключей, source_id дочерних записей и ссылки на наблюдения,
формат DOB, согласованность identifier_match_key с namespace/value/программой.
Неизвестная дата или отсутствующий аэропорт остаются неизвестными.

DuckDB работает с диском, одним потоком и `--memory-limit 1GB` по умолчанию.
Лимит относится к DuckDB, не ко всему Python/PyArrow. Состояние компонентов
использует плотные числовые массивы: parent, size, DOB и флаг неопределённости.
Имена и пересечения документов хранятся для затронутых компонентов. Файлы
пишутся порциями `--batch-size 4000`; сортировки и SQL могут использовать temp.
В реальном каталоге нужно место для входов, старого результата и временной
сборки. Размер временного диска не ограничивается обещанием о RAM.

В 0.6.0 полный пользовательский запуск остановился с OutOfMemoryException на
подготовке наблюдений при 512MB. `list(DISTINCT ...)` хранит состояния агрегации
в RAM и не выгружает их на диск; один temp_directory этого не исправляет
([ограничения DuckDB](https://duckdb.org/docs/stable/guides/performance/how_to_tune_workloads)).
В 0.6.1 документы, происхождение идентификаторов, свидетельства пар и сегменты
собираются по диапазонам не более 16 384 целых групп. Вход упорядочивается по
числовому ключу диапазона, чтобы повторные запросы читали соответствующие группы
строк с диска. Ни одна группа, идентификатор или исходная ссылка не отбрасываются.
Это ограничивает число одновременно открытых агрегатов; объём отдельной группы
и общее потребление Python по-прежнему зависят от данных. Правила решений и
контракты не менялись. `--batch-size` управляет Arrow/Python-записью, а не этой
порционной SQL-агрегацией.

После обновления распакуйте файлы поверх проекта и повторите только T13:

```powershell
python scripts/run_t13.py --require-all
```

Прогон начинается сначала: checkpoint T13 отсутствует. Существующие выходы T11/T12
не удаляйте. Можно явно задать другой лимит DuckDB, например `--memory-limit 2GB`,
если доступная RAM позволяет; повышение лимита не заменяет исправление запросов.
Синтетическая проверка проблемного этапа с тем же числом строк, что в реальном
T12, воспроизводится отдельно (нужен свободный диск для искусственных входов и БД):

```powershell
python scripts/benchmark_t13_memory.py --output data/benchmark/t13_memory_new --report data/benchmark/t13_memory_new/benchmark.json
```

Это проверка подготовки и blocking, а не полного реального T13 или точности
личностей. Сводки — validation/t13_memory_benchmark.json и
validation/t13_memory_compatibility.json; регрессии — validation/t13_memory_pytest.xml.

Большие exact-блоки обходятся устойчивой звездой от минимального observation_id;
это O(n) связей вместо n(n−1)/2. До восьми участников сравниваются все пары.
В DOB-конфликтном блоке дополнительно сохраняется пара с явным противоречием,
даже если у центрального наблюдения DOB отсутствует. Метод не означает, что все
возможные пары были проверены. Ограничения и размеры отражены в blocking_issues.
Для большого блока имён с несколькими оставшимися компонентами уверенная
идентичность отключается. Если весь такой блок уже доказан одним компонентом,
сам размер слабого блока его не дискредитирует.

`max_candidates` ограничивает верхнюю оценку числа сравниваемых пар до генерации
большой таблицы. Превышение останавливает сборку с причиной; строки не отбрасываются
молча. `max_component_size`, `max_name_variants`, `max_trip_group_size` ограничивают
дорогие случаи и оставляют их спорными. Предел массива — менее 2^32 наблюдений.

## Кандидаты и решения по людям

Документ, карта и билет берутся из T12 без удаления нулей/букв. Namespace сохраняет
тип и контекст. Внешний ID, никнейм, общий PNR и билет не являются ключами личности.

| Основание | Решение при отсутствии противоречий |
|---|---|
| Один документ с confirmed namespace типа/издателя | accepted; имя не обязательно |
| Одинаковая программа + номер карты | accepted; имя не обязательно |
| Один source-scoped документ + совпавшие DOB и достаточно похожие имена | accepted в исходном контексте |
| Source-scoped документ без имени или DOB | ambiguous |
| DOB + часть имени, даже при точном полном ФИО | только ambiguous |
| Документ/карта с противоречиями | rejected либо ambiguous, с причиной |

Программа неизвестна — карта не даёт ключа. Равные номера карт разных программ
и 000123/123 различаются. Source-scoped документы не сравниваются между источниками;
подтверждённое общее пространство задаётся в T12, не угадывается T13.

Блок имён строится по полной DOB и трём начальным символам каждого слова
согласованной транслитерации длиной от трёх символов; требуется не менее двух слов.
Похожесть считается только для кандидатов. Используется максимум симметризованного
SequenceMatcher по исходному порядку слов и отсортированным словам. Так небольшая
опечатка не становится ложным конфликтом из-за смены алфавитного порядка токенов.
Пороги конфига: 0,90 для достаточной похожести, менее 0,45 — конфликт.
Это признак строки, не вероятность и не измеренная точность алгоритма.
При сильном идентификаторе промежуточная похожесть остаётся ambiguous.

Карта может быть общей или ошибочной; точный номер не является проверенной
гражданской личностью. Смена документа/имени способна оставить одного человека
в нескольких компонентах. Консервативные отказы и неполное покрытие передаются
дальше вместе с результатом и должны проверяться на реальной выборке.

Разные известные DOB и непересекающиеся документы одного namespace — сильные
противоречия. Набор документов компонента хранит пересечение допустимых значений
для каждого контекста, а не общий union: A={d1}, B={d1,d2}, C={d2} не склеиваются.
Перед каждым объединением проверяются DOB, документы и все известные варианты
имени обоих компонентов. Противоречие A/C не скрывается за безымянным B.
Предыдущая согласованная часть остаётся, новая связь отклоняется/откладывается,
вовлечённые компоненты исключаются из уверенного графа. Конфликт имеет правило,
пару и исходные ссылки; внутренние номера компонентов раскрываются через
person_links.node_index. При превышении лимита вариантов имена не усекаются.

В person_pairs остаётся каждая сгенерированная пара: признаки, похожесть,
accepted/rejected/ambiguous, rule_id и объяснение, хеши точных блоков, ссылки на
идентификаторы и locator обеих сторон. Слабая неоднозначная пара внутри уже
доказанного сильными ключами компонента получает component_support; исходное
прямое решение остаётся в features_json. Незавершённые ambiguous-связи между
компонентами не принимаются.

У каждого observation_id есть ровно один person_links и person_id. Спорные
наблюдения сохраняются, graph_eligible=false. Одиночное наблюдение без опорного
идентификатора также остаётся неопределённым. Надёжная карта или документ может
дать опору без имени; source-scoped документ требует имени и DOB. accepted для
одиночной записи имеет confidence=source_only, объединённой — strong_identifier.
Идентификаторы людей — SHA-256 от минимального observation_id с префиксом person_,
без отображения документа. Стабильность гарантируется для того же набора/правил
независимо от порядка строк, batch_size и повторного запуска. Добавление новых
наблюдений/изменение решений может изменить минимальный якорь и ID.

## Объединение поездок

Каждый travel_id получает ровно один segment_links. Кандидаты находятся внутри
person_id + полная наблюдённая дата + полный номер рейса с перевозчиком.
SU001=SU1; чистое 123 не становится известным рейсом. Номер в другой день — другой
ключ. Отсутствующая дата/рейс даёт отдельную спорную запись.

Сначала рассматриваются полные маршруты и наиболее точные времена. Совместимость
проверяется со всем накопленным сегментом: известные точки не противоречат,
интервалы исходного локального времени/UTC пересекаются с учётом date/minute/second,
билеты одного namespace не противоречат. Разные namespace билетов не объявляются
ни равными, ни конфликтными. Общая бронь не объединяет поездки или людей.

Полные одинаковые наблюдённые маршрут/рейс/дата при совместимых времени/билетах
объединяются. Для неполного маршрута дополнительно нужен общий явный билет в
одном контексте и ровно один совместимый сегмент. Без этого неполная запись
сохраняется отдельно. Date-only свидетельство не соединяет вылеты в 10:30 и 18:30:
при нескольких совместимых сегментах остаётся ambiguous. Слишком большая группа
сохраняется отдельными спорными свидетельствами с trip_group_limit.

Время сравнивается интервалами исходной точности. Секунда внутри известной минуты
совместима с минутой; две разные секунды не совпадают. Из date-only не создаются
полночь/UTC. Итоговое наиболее точное время должно присутствовать в одном из
наблюдений; оно раскрывается через segment_links. Выведенные T11 точки и часы
не используются как наблюдённое доказательство. Если точку дал другой исходный
билетный свидетель, исходная неизвестность первой записи видна в её ссылке.

Свободное поле codeshare не доказывает соответствия номеров. В configs/resolution.yaml
есть пустая секция codeshare_rules. Для включения нужны rule_id, source_id (* явно
разрешает все), marketing_flight, operating_flight, две точные IATA-точки, ISO
valid_from/valid_to, reason и evidence. Периоды включительны; пересекающиеся
правила одного маршрута/номера запрещены. Правило применяется к исходному номеру
один раз, только в своей дате/маршруте, ID правила сохраняется в segment_links.

segment_id — SHA-256 минимального travel_id с префиксом segment_. Все свидетельства
сохраняют event_kind, status_raw, точность и качество T11. Итоговый boarding_record_present
означает наличие посадочной записи, не доказанную физическую посадку. Бронь,
форум и начисление баллов не равны отмене либо посадке. По умолчанию graph_eligible
требует уверенного person_links, установленного события с двумя наблюдёнными
точками и посадочной записи boarding_record/boarding_pass_record. Противоречивые
локальные времена DST/offset отключают уверенное событие. Список допустимых
типов свидетельств задаётся явно, и его хеш хранится в отчёте.

## Независимая проверка 100 пар

Выполняется стратифицированный отбор: 50 accepted, 30 ambiguous, 20 rejected
из реально созданных сопоставимых кандидатов. Внутри слоя сортировка SHA-256 от
seed + pair_id, затем pair_id. В CSV — источник, исходное имя/DOB, locator, признаки
и ссылки на свидетельства. Если в слое не хватает пар, CSV короче, shortages
показан явно. Дополнять выборку вымышленными решениями нельзя.

В data/processed/resolution_review_sample.csv лежит неизменяемый снимок отбора,
в data/review/person_pairs.csv — копия для Кирилла. reviewer_decision, reviewer_name,
reviewed_at и reviewer_notes изначально пусты. Программа не выдаёт собственные
решения за проверку Кирилла и не отправляет ему сообщений. При повторном запуске
редактируемый CSV сохраняется. Для другого fingerprint создаётся новое имя с
суффиксом; актуальный путь напечатан в итоге и resolution_report.review.editable_csv.

Проверяющий открывает исходные свидетельства по locator и заполняет четыре
reviewer-поля. Решения: accepted/rejected/ambiguous, дата — ISO datetime.
Разногласия фиксируются в notes и обсуждаются командой. Затем:

```powershell
python scripts/audit_t13.py
# Если файл имеет суффикс, передать путь из итогового отчёта:
python scripts/audit_t13.py --sample data/review/person_pairs.RUN.csv
```

Этот запуск не пересчитывает T13. Проверяются хеши снимка/отчёта, fingerprint,
полнота и уникальность пар; исходные доказательства/решение автора нельзя менять.
Сохраняются матрица решений, непросмотренные пары, разногласия, ошибки склеивания
на просмотренных accepted-парах и условная precision по однозначным ответам.
Без ответов метрика null. Матрица относится только к проверенной выборке;
стратифицированный набор не даёт точности всего массива. Окончательная подпись
и независимость проверяющего подтверждаются людьми, не полем reviewer_name.

## Файлы и передача дальше

| Файл | Назначение |
|---|---|
| persons.parquet | Один внутренний человек/неопределённый singleton, якорь и качество |
| person_links.parquet | Все исходные наблюдения, person_id, правило, уверенность, locator |
| person_pairs.parquet | Все сравнения, признаки и объяснимые решения |
| segments.parquet | Различимые поездки, наблюдённые поля, типы свидетельств и доступность графа |
| segment_links.parquet | Все travel_id и происхождение их объединения |
| conflicts.parquet | Свидетельства несовместимости людей/поездок/ограничений |
| blocking_issues.parquet | Размеры и причины ограниченного/спорного поиска |
| resolution_report.json / resolution_summary.txt | Балансы, покрытие, статусы, upstream-ограничения и ревью |
| resolution_manifest.json | Версии и SHA-256 всех опубликованных файлов T13 |

Финально проверяются PK/FK, количество person_links=observations и
segment_links=travel_observations, одинаковые person_id во всех связанных
таблицах, source_id/source_record_id/locator и отсутствие DOB-конфликтов внутри
компонента. Объединённые свидетельства не вычитаются из link-таблиц. Исходные
таблицы T11/T12 сохраняются. Неподтверждённый PDF из отчёта T12 передаётся как
upstream-ограничение; ошибки readers не становятся новыми ошибками T13.

T15 получает segments по person_id и признаки пропусков/точности; неоднозначные
сегменты нельзя считать точным числом перелётов. T18 фильтрует graph_eligible=true
и использует segment_id один раз. T14 получает все ссылки, конфликты и покрытие
по источникам. Паспорта/имена и ID не становятся признаками поведения.

Публикуются только файлы T13 с откатом замен при исключении, manifest последним.
Потребители проверяют нужные хеши и не читают во время обновления каталога.
OS-lock .resolution.lock совместим с Windows/Unix и освобождается при завершении
процесса; само наличие файла не запрещает запуск. После прерывания начать заново:
checkpoint T13 пока нет. Диагностика — resolution_last_failure.json.

## Проверки

```powershell
python -m pytest -q
python -m pytest -q tests/test_matching.py
python scripts/benchmark_t13.py --people 20000
```

Нагрузочный тест строит искусственные входы и запускает T13 отдельным процессом,
проверяя число людей/сегментов, тихий режим и RSS на Linux. Протоколы:
validation/t13_benchmark.json и validation/t13_validation.json. Это не замер
полных реальных 2,75 млн профилей и не оценка качества их сопоставления.
