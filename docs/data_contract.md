# Контракт данных 1.0 (T04)

Авторитетные схемы — `src/yoyoflot/contracts.py`. Версия хранится в metadata
каждого Parquet. Изменение несовместимого типа/смысла требует новой версии и
обновления всех потребителей. Поля, отсутствующие в источнике, остаются null;
неизвестное не означает «нет», ноль или пустую строку.

## Интерфейс reader

```python
from yoyoflot.contracts import TableBatch

def read(path, source_id, batch_size=1000, **options):
    yield TableBatch("person_observations", records, counters={"input_rows": 10})
```

`records` — список словарей по известной схеме; `TableBatch.to_arrow()` проверяет
неизвестные поля, ключи, ссылки и строковые типы. `counters` — приращения
счётчиков, не накопительные итоги. Reader выдаёт независимые таблицы,
не объединяет людей между источниками и не назначает person_id или score.
Таблицы связываются через локальный `observation_id`. Пример минимального
подключения — `boarding_csv.read`, регистрация CLI — список `READERS`.

## Ключи и происхождение

| Таблица | Первичный ключ | Связи и смысл |
|---|---|---|
| person_observations | observation_id | Один профиль/исходная строка человека, даже без имени/рейсов |
| identifiers | identifier_id | observation_id → person_observations; один документ/билет/карта |
| travel_observations | travel_id | observation_id → person_observations; необязательный loyalty_identifier_id → identifiers |
| schedules | schedule_id | Отдельная строка расписания; не факт поездки пассажира |
| provenance | entity_table + entity_id + source_record_id | Связь объекта с исходной записью и версией преобразования |
| errors | error_id | Ошибка/предупреждение/исключение конкретного locator |

Во всех таблицах `source_id`, `source_record_id`, `locator` обязательны;
`raw_json` содержит исходные поля (не использованные поля также сохраняются).
`source_record_id` и ключи объектов — SHA-256 от JSON-кортежа
`[source_id, sha256_полного_входа, locator, kind]` в UTF-8. Они стабильны при
повторном чтении одной версии и независимы от порядка выдачи порций.
Изменение входных байтов создаёт новую версию и новые идентификаторы;
это не глобальные ключи пассажиров. Смена batch_size не изменяет ключи.

Locator CSV/Sirena — физическая строка, начиная с 1; CSV хранит диапазон строк
для записей с переносами в кавычках. JSON — ключ профиля с экранированием
JSON Pointer и ключ/индекс вложения. XML — ordinal пользователя и путь с
индексами, независимый от пространств имён. YAML — номер документа/дата/рейс/FF.
XLSX — архив/имя книги/лист/физическая строка; PDF — страница/строка расписания.
`provenance` содержит ссылку на каждый объект и каждый элемент errors.
Индекс YAML-карты/JSON-рейса начинается с 0, XML/PDF/XLSX-строки — с 1.

## Строки, время и свидетельства

Документы, внешние ID, билеты и карты — строки. `000123` не становится `123`.
Внешние пробелы карты удаляются, полное исходное значение остаётся в raw_json.
Программа карты хранится отдельно; ключ сопоставления в T13 должен включать
programme + value. Числовой идентификатор Excel переводится в десятичную
строку с явным предупреждением, без восстановления неизвестных цифр/нулей.

`*_raw` — исходное значение; `*_local` — ISO-строка с исходной точностью.
`*_precision`: date, minute, second, invalid или null. Дата без времени остаётся
`YYYY-MM-DD`, без полуночи и без UTC. Неверная дата сохраняется как raw,
local=null, precision=invalid и регистрируется в errors. Часовой пояс пока null:
из страны/города он не выводится. Birth date также ISO date или null; BoardingData.csv использует подтверждённый
формат MM/DD/YYYY, остальные readers — явные форматы своих источников.
Нормализация имени сейчас только схлопывает пробелы и приводит к casefold;
транслитерация и объединение правил — T12.

`event_kind`: boarding_record, registered_flight, loyalty_activity,
reservation_record, exchange_record, boarding_pass_record. Эти названия описывают
источник свидетельства и не подтверждают фактическую посадку. STATUS сохраняется
как `status_raw`; его семантика не доказывает посадку конкретного пассажира.

## Запись, ошибки и восстановление

Запись в Parquet порциями; пустые таблицы создаются с полной схемой. Журналы
содержат reason, severity (info/warning/error), locator и raw payload.
Принятые записи могут одновременно содержать ошибки отдельных дат/полей.
Поэтому число errors нельзя вычитать из количества исходных строк: смотреть
причины ошибок и отдельные входные/выходные счётчики.

Публикация каталога происходит после закрытия writers и повторной проверки
SHA-256 входа. При исключении нет успешного manifest, прежний финальный каталог
сохраняется, диагностический `.partial` остаётся. Каталоги `.backup` при аварии
между двумя rename требуют восстановления: сохранить оба каталога, сверить
manifest и вернуть завершённый `.backup`, если основной отсутствует. Не удалять
его автоматически. Одновременные writers на один output не поддерживаются.
Для PDF checkpoint состоит из атомарно сохранённых порций JSON и checkpoint;
порция без checkpoint повторно перезаписывается. В сборку попадают только
ожидаемые порции текущего SHA-256/конфигурации; весь результат в RAM не собирается.

## CSV / JSONL / Parquet

Parquet — типизированный основной формат. JSONL — один JSON-объект на строку,
с `null`, bool и int исходных типов. CSV UTF-8: `\N` — null, `True`/`False` —
bool, integer-поля восстанавливаются по контракту. Пустая строка отличается
от null. CSV не является типизированным: читать идентификаторы как строки.
Буквальный `\N` в строковом поле неоднозначен в CSV; для точного восстановления
такой редкой строки использовать JSONL/Parquet. PDF-тест сверяет все поля
между тремя форматами, включая неизвестный период и arrival_day_offset.

## Память и измерения

CSV/Sirena читают последовательно; JSON держит один профиль, XML — одного user,
YAML — один рейс (максимум 100000 nodes, глубина 50), XLSX — один seekable файл
книги и поток OOXML без полной модели. Общие стили/shared strings одной книги
могут занимать память своего размера. Полные измерения шести настоящих входов:
validation/real_runs.json (121.2–210.9 МиБ RSS, отдельные процессы).
process_peak_rss_mib — пик процесса, включая импорт библиотек; при ingest all
он включает предыдущие readers. На Windows resource недоступен: RSS=null.

## Дополнение T11: geography 1.0

Контракт readers 1.0 и их таблицы остаются неизменными. T11 создаёт отдельные
travel_geography, schedule_geography, schedule_links и place_inventory.
Авторитетные дополнительные Arrow-схемы — `normalize/geography.py` (META,
EXTRA_FIELDS, LINK_SCHEMA, INVENTORY_SCHEMA); правила — `normalize/airports.py`.
Metadata этих файлов: geography_contract_version=1.0, rule_version=airports:1.1.
В правилах 1.1 проверенные варианты страны при явном коде аэропорта имеют
status=corrected, reason=verified_country_alias. В *_override_json сохраняется
объект с country_aliases (массив полных правил); при совместном исправлении
кода исходное правило находится в airport_override. Без country alias формат
прежнего одиночного правила сохраняется. Базовая Arrow-схема не изменилась.

Все исходные колонки сохраняют типы и значения; дополнительные колонки T12
пропускаются через pa.unify_schemas при совместимых типах. Неизвестная форма
базовых колонок даёт ошибку, а не неявное приведение. T11 не назначает person_id,
не объединяет пассажиров и не считает schedules наблюдением поездки.
Ключи travel_id/schedule_id не меняются; повторный вход с тем же ключом запрещён.
Строка travel_geography соответствует ровно одной исходной travel_observations.
Для schedule_links ключ пары travel_id + schedule_id уникален в одном запуске.

Связь содержит provenance обеих сторон и JSON заполненных полей. Статус
inferred_from_schedule хранится у выведенной точки и/или времени; исходные raw и
local не заменяются. Дата без времени остаётся датой в source-колонке, а новый
*_effective_local может дополнить её часами только по явно помеченному правилу.
UTC остаётся null при недостаточной точности, DST-неоднозначности или конфликте.
Справочник версионируется по SHA-256; ручные исправления имеют evidence/reason.

Потребители T13/T15/T18 читают таблицы через t11_manifest.json с проверкой SHA-256
и сохраняют признаки качества/происхождение. Для дневного исходного наблюдения
выведенные расписанием часы нельзя считать фактом посадки или основанием точного
совместного события. Полные правила, знаменатели покрытия и запуск — geography.md.

## Дополнение T12: canonical 1.0

Авторитетные схемы — `normalize/canonical.py::SCHEMAS`, версии правил — values.py
и configs/normalization.yaml. Это отдельный контракт canonical_contract_version=1.0;
таблицы и версия readers T04 остаются неизменными. Наблюдения людей переименованы
в observations, ключ observation_id сохранён. provenance.entity_table отражает
канонические имена, исходное имя доступно в source_values_json.

Обязательны строковые PK/source_id/source_record_id/locator и observation_id
дочернего идентификатора/поездки. Неключевые поля nullable: несовместимое значение
не удаляет профиль, а становится null с normalization_errors и сохранённым
оригиналом. Исходные корректно типизированные raw/JSON-колонки остаются без
изменений. Нормализация имени/идентификатора создаёт дополнительные представления;
даты и precision проверяются по источнику и сохраняют исходную точность.

source_values_json восстанавливает изменённые базовые поля; дополнительные поля
входа сохраняются с префиксом extra:. normalization_rules_json указывает правила
затронутых полей; normalization_version + config_sha256 фиксируют рецепт.
transformation_log содержит числа принятых затронутых строк и примеры до/после;
поле exceptions считает ошибки, а не исключённые профили. errors readers и
normalization_errors разделены. orphan-reference не исчезает без следа.

Повтор PK с полностью одинаковыми значениями удаляется; противоречащие копии
одного PK — ошибка сборки. Разные исходные PK не объединяются по похожести.
T13 получает все межисточниковые свидетельства, namespace и качество; новые
person_id и segment_id в T12 не назначаются. Для каждой сущности и source_id
сохраняется баланс input_rows=output_rows+duplicates_removed.
Правила, запуск, namespace и ограничения — transformations.md.

## Дополнение T13: resolution 1.0

Авторитетные Arrow-схемы — resolve/common.py::SCHEMAS; metadata:
resolution_contract_version=1.0, resolution_version=resolution:1.0. Readers,
canonical и geography сохраняют свои версии. Входы проверяются по нужным файлам
canonical_manifest/t11_manifest; T11 должен быть производным выбранного T12.
Большая schedule_links не нужна для разрешения личности и не читается T13.

person_links имеет ровно одну строку на observation_id, segment_links — на
travel_id. persons/person_id и segments/segment_id связаны через эти таблицы
с source_id/source_record_id/locator и сохранёнными upstream-ключами. ID
детерминированно получены из минимального исходного ID компонента, без номера
документа. Стабильность — для одного снимка/правил при перестановке строк и
изменении размера порции; инкрементальное расширение не обещает вечного ID.

person_pairs хранит каждую сгенерированную пару и решение accepted/rejected/
ambiguous, признаки, правило, причину и ссылки на свидетельства. Точные блоки
документа/карты сохраняют namespace/нули. DOB+имя — вспомогательный блок, не
самостоятельное доказательство. Компонент проверяется целиком по DOB, пересечению
документов каждого namespace и всем вариантам имени. Спорные наблюдения имеют
person_links.graph_eligible=false, даже если прежняя согласованная часть объединена.
node_index служит только внутренней ссылкой из диагностик на observation_id.

segments не создаёт фактов поездки из расписания. Время/маршрут для объединения
должны быть наблюдены; вывод T11 явно отличим в segment_links и не становится
основанием совпадения события. Для неполного маршрута нужен общий билет того же
контекста и единственный совместимый сегмент. Date-only не превращается в
полночь; интервалы исходной точности проверяются на всём сегменте. Marketing и
operating номера объединяются только по подтверждённому правилу с маршрутом/
периодом/источником/evidence. Свободный codeshare и общая бронь недостаточны.

graph_eligible в segments требует допустимых person_links, известной наблюдённой
даты/рейса/двух точек и разрешённого типа свидетельства (по умолчанию посадочная
запись). Это критерий доступности анализа, не утверждение физической посадки или
проверенной гражданской личности. event_kinds_json, точности, статусы исходного
времени и конфликты обязательны для последующих потребителей T14/T15/T18.

conflicts и blocking_issues описывают спорные решения/ограничения. Они не удаляют
профили и не вычитаются из балансов. В resolution_report раздельны техническое
complete, upstream-ограничения, покрытие и ожидаемое независимое ревью 100 пар.
Шаблон CSV не считается проверенной разметкой. Метрики audit_t13 относятся
только к реально просмотренной выборке; точность всего массива не выводится.
Публикация и проверка хешей — через resolution_manifest.json; подробности — matching.md.
