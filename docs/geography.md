# T11: география и осторожные связи с расписанием (контракт 2.0)

## Запуск

Из корня проекта после установки зависимостей:

```powershell
python -m pip install tzdata==2026.5
python scripts/run_t11.py
```

Скрипт работает кнопкой Run в PyCharm. По умолчанию читает `data/interim/real`,
если каталог существует; иначе `data/interim`. Он не запускает повторный разбор
PDF и других исходников. Для полного запуска необходимы готовые Parquet readers.
Пустой или неверный вход даёт понятную ошибку и код 1.

```powershell
python scripts/run_t11.py --input data/interim/real --output data/processed
python scripts/run_t11.py --input data/interim/real -q
python scripts/run_t11.py --input examples/interim --output data/processed/demo_t11
```

Обычный запуск печатает итог и при долгой работе не чаще одного сообщения о прогрессе за 30 секунд; тот же текст записывается в
`geography_summary.txt`. `-q`/`--quiet` отключает успешный консольный вывод целиком,
файлы сохраняются. Ошибки сообщаются в stderr с ненулевым кодом.

После установки проекта доступна эквивалентная команда:

```powershell
python -m yoyoflot airports --input data/interim/real --output data/processed
```

Для T12 используется плоский каталог его таблиц. Чтобы подтвердить покрытие
расписания, передать исходный schedules.parquet с соседним source_report.json:

```powershell
python scripts/run_t11.py --input data/processed --schedules data/interim/real/timetable_pdf/schedules.parquet
```

Несколько независимых входов допускаются после `--input`, несколько PDF — после
`--schedules`. Нельзя одновременно передавать один и тот же каталог через родителя
и напрямую. Повторные travel_id/schedule_id приводят к ошибке, а не к размножению
наблюдений. Каталоги `.checkpoint`, `.partial`, `.backup` не читаются. Наличие
папки real не означает, что в ней доступны все шесть персональных источников:
покрытие отражено по фактически прочитанным source_id.

## Справочник и ручные правила

Локальный `data/reference/airports.csv` получен из OpenFlights airports.dat.
Источник: https://openflights.org/data.php ; исходные байты, ODbL-1.0,
атрибуция, дата получения, число строк и SHA-256 лежат рядом в
`reference_manifest.json`, `openflights_airports.dat`, `LICENSE-OpenFlights.txt`.
Производный справочник распространяется по ODbL-1.0.
Повторная сборка CSV из сохранённых исходных байтов с проверкой полного совпадения:
`python scripts/build_airport_reference.py` (сеть не используется). Дата получения не является
датой актуальности: upstream — статический снимок, точная дата всего снимка не
известна. Это не сертифицированный исторический реестр: смены кодов, закрытия и
координаты на дату поездки независимо не подтверждены. Нет обещания 100% покрытия.

IATA и ICAO проверяются по справочнику, а не по длине строки. Поддержаны точные
названия аэропортов, городов и именованные поля JSON (`Airport`, `IATA`, `ICAO`,
`AirportCode`, `City`, `Country`, также перечисленные в коде строчные варианты).
Применяется NFKC, регистронезависимое сравнение и схлопывание пробелов. Нет fuzzy
matching, самостоятельной транслитерации или автоматического выбора ближайшего
аэропорта. Противоречащие друг другу коды/контекст не принимаются.

Город с несколькими аэропортами имеет `kind=city`, `status=ambiguous` и список
всех airport_id. Страна сохраняется как страна, без аэропорта/координат/пояса.
Уникальный город может быть связан только с единственным аэропортом **данного
снимка**, это не утверждение об отсутствии других аэропортов в реальном мире.
Статус `exact` относится к точному справочному соответствию; `kind` отличает
исходный город от исходного аэропорта.

Секция `airport_overrides` в `configs/airports_overrides.yaml` пуста:
замены аэропортов не добавлены. Каждая включённая запись требует `source_id`, `original`,
`target_iata`, `reason`, `evidence`. `*` означает все источники, правило конкретного
источника имеет приоритет. Некорректные/повторные правила и неуникальные цели
отклоняются. Полное правило сохраняется в `*_override_json`; исходное значение
остаётся в `*_raw`. Ручное правило не может быть заменой проверки контекста.

В правилах `airports:1.1` добавлена секция `country_aliases` с десятью проверенными
вариантами страны из реального forum_json. Поля: `source_id`, `original`,
`target_country`, `reason`, `evidence`. Правило используется только в именованном
Country/country рядом с явным уникальным кодом из справочника. Оно проверяет
страну этого аэропорта, не выбирает аэропорт по городу и не исправляет код.
Статус места — corrected, причина — verified_country_alias, все применённые
правила — в *_override_json.country_aliases. При совместной замене кода его
правило сохраняется в airport_override. Пустой Country означает отсутствие
контекста; реальный непокрытый правилом конфликт по-прежнему блокирует выбор.
Если оба варианта страны уже встречаются в снимке (Myanmar/Burma), необходимо
явное `reference_name_variant: true`; точное совпадение страны не меняется.
Строки United, Ko, Mold, Co и неоднозначные территории не сопоставляются догадкой.

Проверка присланных geography_report.json и place_inventory.parquet описана в
`validation/t11_real_inventory_review.md` и `.json`. Все 13 835 уникальных мест
сопоставлены повторно с исходными частотами. Для forum_json точные + исправленные
места составили 95,38% вместо 54,66%; это проверка инвентаря, не полный повторный
расчёт UTC/расписания. Это исторический протокол предыдущего снимка; новый
полный запуск фиксируется отдельно в `validation/backend_validation.json`.
Старая geography не обновляется сама от замены кода. Для отдельных запусков
на уже подготовленных readers доступны команды:

```powershell
python scripts/run_t12.py --require-all
python scripts/run_t11.py --input data/processed --schedules data/interim/real/timetable_pdf/schedules.parquet
```

Повторная загрузка исходников в readers не требуется. По присланному отчёту все
63 403 248 ссылок — reference_only; это кандидаты для справки, они не заполняют
исторические поля. PDF source_report имеет incomplete, поэтому автоматический
вывод по расписанию дополнительно запрещён до подтверждения его полноты.

## Выбор строки расписания

1. Номер включает префикс перевозчика: AB00123 = AB123, но AB123 ≠ XY123.
   Чистый номер без перевозчика не сопоставляется (если T12 явно передал `carrier`,
   он может дополнить номер). Звёздочка не обозначает известного operating carrier.
2. `codeshare` служит дополнительным номером только если содержит полный явный
   код вроде XY123. `true`, `1`, `*` и свободный operated_by не дают новой связи.
   Marketing и operating номера автоматически не объединяются.
3. Обе точки строки расписания должны существовать в справочнике, parse_status
   должен быть `ok`; известные точки наблюдения ограничивают кандидатов. Для
   неоднозначного города допустим любой аэропорт его списка, но исходный город
   сам по себе не превращается в выбранный IATA. Неизвестное непустое место
   блокирует подбор вместо молчаливого игнорирования.
4. Нужны полная дата отправления, включительный valid_from/valid_to и явные дни
   недели SkyTeam: 1=воскресенье, 2=понедельник, 3=вторник, 4=среда,
   5=четверг, 6=пятница, 7=суббота (легенда исходного PDF, страница 3).
   `days_of_week` сохраняет цифры источника; при сопоставлении календарной даты
   её ISO-день преобразуется как `isoweekday() % 7 + 1`.
   Исходные часы, если есть, должны совпасть;
   исходная дата прилёта должна согласоваться с явным +N. Диапазон без года,
   перевёрнутый диапазон и неизвестные дни не подтверждают покрытие.
5. Строки вне периода имеют `reference_only` и **не заполняют** маршрут/время.
   Неизвестный период — `temporal_unknown`. Несколько совместимых строк (включая
   неизвестный период) — `ambiguous`, даже если выглядят похоже. Сохраняются все
   совместимые кандидаты с их schedule_id. Несовместимые по точкам/часам/дню
   недели кандидаты не становятся ссылками.
6. Для автоматического заполнения также требуется подтверждение полноты всего
   переданного корпуса расписания: соседний source_report.json, status=complete,
   совпадающее число schedules, полный проход pages/total_pages, отсутствие
   исключённых страниц/ошибок извлечения. Отсутствие отчёта, `incomplete` или
   частичный корпус запрещает автоматическое заполнение даже при одном кандидате.
   В частности, PDF с 704 непроверенными страницами не доказывает единственность.
7. Только единственная совместимая строка с подтверждённым покрытием получает
   `matched`. Заполняются лишь отсутствующие аэропорты. Для локального времени
   создаются **новые** `*_effective_local`/`*_effective_precision`: время из
   расписания может дополнить дату или отсутствующее время при известной дате
   отправления. Прилёт требует явного arrival_day_offset; отсутствие +N не равно
   нулю. Существующая дата/точное время не перезаписываются. Вывод времени отмечен
   `*_time_origin=inferred_from_schedule`, не равен наблюдённому времени.

Многоучастковые рейсы остаются отдельными строками. Нельзя выбирать первый
участок по совпадению номера. Связи содержат исходные ключи обоих объектов,
locator, правило выбора, temporal_coverage, JSON всех заполненных полей и
свидетельства из строки расписания. schedule_id ведёт обратно к исходному
`schedules.parquet` и далее reader provenance. Корректировка места ссылается на
правило YAML; координаты/пояс — на airport_id и версию справочника.

## UTC и качество для T15/T18

UTC вычисляется только для полной локальной даты и времени с точностью minute
или second и известного аэропорта/пояса. Используются исторические правила IANA
из закреплённого пакета tzdata 2026.5 (на Windows также); fallback к системной базе
отмечается в отчёте, если пакет не установлен. На повторённом при переводе часов
времени проверяются оба fold: неоднозначность остаётся null. Несуществующее время
во время скачка вперёд также null. Явный UTC offset источника может разрешить fold,
только если он согласуется с IANA. Конфликт исходного departure/arrival_timezone
со справочником не замалчивается. Неполная дата, дата без часов, неизвестный пояс
и неизвестный аэропорт остаются нерешёнными; запрещено подставлять полночь.

`geography_complete` означает известность обеих точек; `geography_inferred` — что
есть точка из расписания. `time_complete` означает два разрешённых UTC timestamp,
`time_inferred` — наличие времени из расписания. Эти флаги не доказывают поездку
или посадку. T15/T18 должны учитывать происхождение, полноту и исходную точность:
расписание не становится фактом реального вылета и не доказывает совместную поездку.

## Выходные файлы и баланс

| Файл в data/processed | Содержание |
|---|---|
| travel_geography.parquet | Одна строка на travel_id, все исходные поля плюс география/UTC/флаги и ссылка на общую группу кандидатов вне периода |
| schedule_geography.parquet | Одна строка на schedule_id, исходные поля плюс origin_geo_*/destination_geo_* |
| schedule_links.parquet | Отдельные связи, кроме вынесенных в группы кандидатов вне периода; provenance и правила каждого вывода |
| schedule_reference_groups.parquet | Общие наборы справочных ссылок вне периода: group_id, число членов и неизменные статус/правило/причина |
| schedule_reference_members.parquet | Пары group_id + schedule_id, без повторения исходного payload для каждой поездки |
| place_inventory.parquet | Уникальные исходные места по source_id/таблице/полю, частоты и вид места |
| geography_report.json | Количества, доли, входные SHA-256, версии, покрытие расписания, ограничения |
| geography_summary.txt | Краткий итог, совпадающий с консолью |
| t11_manifest.json | SHA-256 всех опубликованных файлов T11 |

Инвентарь охватывает origin_raw/destination_raw шести персональных readers и
origin/destination/города/страны расписания. Произвольные неописанные ключи raw_json
не интерпретируются как аэропорты. Пустые значения входят в баланс явно.
Доли для поездок по каждому source_id имеют знаменатель `2 × число поездок`:
exact + corrected + inferred + unresolved = 1; ambiguous/missing входят в
unresolved, точные причины доступны отдельно. Для PDF аналогичный отдельный
`schedule_by_source` считает две точки на строку расписания. Доли не выдаются
за покрытие исходных персональных профилей или всех аэропортов мира.

### Ссылки вне периода без многократного копирования

В контракте `geography_contract_version=2.0` правила сопоставления остаются
`airports:1.1`. По умолчанию связи с `temporal_coverage=outside_period` хранятся
нормализованно. Это только справочные кандидаты: они по-прежнему не заполняют
маршрут или время поездки и не подтверждают посадку.

В `travel_geography` поля `schedule_reference_group_id` и
`schedule_reference_count` указывают на общий набор совместимых кандидатов
вне периода. Один набор может использоваться многими поездками.
`schedule_reference_groups.member_count` равен числу строк этой группы в
`schedule_reference_members`; каждая пара `group_id + schedule_id` уникальна.
Нет такой связи — ID группы равен `null`, число ссылок равно 0.
Исходные строки расписания полностью остаются в `schedule_geography`.
Связи с неизвестным периодом/датой не переводятся в `outside_period`:
они остаются отдельными кандидатами и продолжают влиять на неоднозначность.

Полная прежняя связь восстанавливается соединением
`travel_geography → schedule_reference_groups → schedule_reference_members → schedule_geography`.
Provenance поездки берётся из `travel_geography`, provenance расписания — из
его исходной строки; `evidence_json` восстанавливается в том же каноническом
JSON-формате. Поля группы всегда имеют `status=reference_only`,
`temporal_coverage=outside_period`, `reason=outside_schedule_period` и
`filled_fields_json={}`. Маршрут, явный codeshare, наблюдаемые часы и смещение
даты прилёта проверяются до включения кандидата в группу.

Для потребителя полного отношения доступен потоковый декодер:

```python
from yoyoflot.normalize.geography import iter_schedule_links

links = iter_schedule_links("data/processed", batch_size=2000)
first_link = next(links, None)
```

Он выдаёт обычные словари старого `schedule_links`, включая полное
`evidence_json`, без создания развёрнутого файла. Порядок выдачи строк не
является частью контракта. Полный обход по-прежнему имеет стоимость полного
логического отношения: группировка сокращает хранение, а не число возможных
связей. В Python-API `run(..., compact_reference_links=False)` оставлен явный
плотный режим для проверки эквивалентности; при нём оба групповых файла пусты.

В `geography_report.json` различаются:

| Счётчик | Значение |
| --- | --- |
| `counts.schedule_links` | Число физических строк `schedule_links.parquet` |
| `counts.schedule_reference_groups` | Число общих групп |
| `counts.schedule_reference_members` | Число пар группа–строка расписания |
| `counts.schedule_reference_associations` | Сумма `schedule_reference_count` по всем поездкам |
| `counts.logical_schedule_links` | `schedule_links + schedule_reference_associations`: прежнее число связей |

Счётчики `by_source.*.schedule_links` сохраняют логическое число связей по
статусам. Нельзя сравнивать один только физический счётчик с прежним объёмом
свидетельств. Все новые файлы входят в `t11_manifest.json` и снимок T16.

Чтение Parquet идёт порциями; индексы расписания/уникальных ID и агрегации мест —
временная SQLite на диске. Кандидаты предварительно фильтруются SQL-индексом по номеру и известным точкам.
Кеш кандидатов ограничен бюджетом 24 МиБ сериализованных данных; отдельно
до 8 МиБ для JSON свидетельств и 32 МиБ для результатов совместимости вне
общего известного периода расписания. Компактный режим использует отдельный
кеш до 32 МиБ, сохраняющий только ID группы и число ссылок; объекты расписаний
для каждого такого ключа не удерживаются. Оба кеша учитывают маршрут, номера,
наблюдаемые часы и относительную дату прилёта; хотя бы один неизвестный или
перевёрнутый пригодный период отключает эту оптимизацию. Неизвестная дата
поездки также не позволяет использовать её. Фактические Python-объекты занимают больше места,
это не предел RAM всего процесса. SQLite использует кеш до 64 МиБ; кеш мест — 50000.
Индексы уникальности строятся одним проходом после загрузки; дубликаты по-прежнему
блокируют публикацию. SQLite — только временная рабочая база: для неё отключены
журнал и синхронная запись, при ошибке/прерывании она полностью отбрасывается.
Опубликованные данные/manifest не хранятся в этой базе. Исходные колонки Arrow,
включая raw_json и дополнительные поля T12, переносятся без преобразования
каждого значения в Python и обратно.
Нет полного объединения миллионов поездок в RAM. Возможное множество кандидатов
одного номера остаётся в памяти; это ограничение отражено в реализации.
Входные хеши проверяются повторно перед публикацией. T11 заменяет только свои
девять файлов и сохраняет canonical tables T12, readers и checkpoint. Ошибка до
публикации оставляет прежний результат; исключение при публикации откатывает
замены. Manifest публикуется последним: потребитель проверяет его SHA-256 перед
чтением. Несколько файлов не образуют атомарный снимок для параллельного reader;
не читать каталог во время обновления. `.t11.lock` используется для блокировки средствами ОС (Windows msvcrt / Unix flock).
Файл остаётся на диске, но его наличие не запрещает запуск: владение освобождается
при закрытии процесса, в том числе после Ctrl+C или принудительного завершения.
Пустые lock-файлы предыдущей версии совместимы; удалять их не требуется.
Активный writer блокирует второй процесс. Не удалять файл во время работы T11:
это может нарушить взаимное исключение. Ctrl+C возвращает код 130 без traceback;

## Проверка и ограничения приёмки

```powershell
python -m pytest -q
python -m pytest -q tests/test_airports.py
```

Сценарии проверяют несколько аэропортов города, ручные правила, неизвестные
коды, два маршрута AB123, отдельные участки, codeshare, время через полночь,
другой период PDF, неизвестные дни/период, частичное покрытие, DST fold/gap,
исторический часовой пояс Москвы, provenance, баланс, повторный запуск и тихий CLI.
Исходный архив преподавателя закреплён в `scripts/dataset_manifest.json`.
Результаты полного прогона и проверки географии фиксируются в
`docs/validation/backend_validation.json`; исторические протоколы не заменяют
проверку нового снимка. Описание обнаруженных дефектов и регрессий находится
в `docs/validation/backend_review.md`.
