# T12: канонические таблицы и журнал преобразований, версия 1.0

## Запуск

Используются **готовые Parquet readers**, исходные CSV/XML/JSON/PDF не парсятся
повторно. Из корня проекта:

```powershell
python scripts/run_t12.py
python scripts/run_t12.py --input data/interim/real --output data/processed --require-all
python scripts/run_t12.py -q
```

Кнопка Run в PyCharm поддерживается. Без аргументов вход — `data/interim/real`,
если он существует, иначе `data/interim`. Выход — `data/processed`; конфигурация —
`configs/normalization.yaml`. Все шесть персональных readers подключаются через
одинаковый контракт. Можно начать с CSV/XML: несколько каталогов передаются
после `--input`. Неприсутствующие источники перечисляются в отчёте, а
`--require-all` запрещает публикацию неполного комплекта персональных источников.
Наличие всех шести — проверка состава, не независимая приёмка качества входов.

После установки проекта эквивалентная команда:

```powershell
python -m yoyoflot build --input data/interim/real --output data/processed --require-all
```

Параметры `--batch-size 4000` и `--memory-limit 512MB` управляют порцией Python
и лимитом DuckDB. Лимит относится к DuckDB, не ко всей памяти Python/PyArrow.
Обработанные таблицы не собираются целиком в Python. Внешняя сортировка/агрегация
DuckDB может использовать временный диск. Проверка повторных ключей сначала
читает только PK, а полная DISTINCT выполняется лишь при их наличии.

Обычный запуск выводит итог и не чаще одного сообщения прогресса за 30 секунд
на границах порций/этапов; отдельная долгая SQL-операция может идти без сообщений.
Тот же итог сохраняется в `canonical_summary.txt`. `-q`/`--quiet` полностью
отключает успешный консольный вывод, файлы сохраняются. Код 0 — complete;
1 — complete_with_errors (файлы созданы с явными проблемами) либо failed;
130 — прерывание пользователем. `canonical_report.json` различает эти состояния.

## Выход и передача другим задачам

| Файл в data/processed | Содержание |
|---|---|
| observations.parquet | Наблюдения людей, без назначения person_id |
| identifiers.parquet | Документы, билеты, карты и контекстные ключи сравнения |
| travel_observations.parquet | Исходные свидетельства поездок с очищенными значениями |
| schedules.parquet | Только расписание; строки PDF не создают пассажиров |
| provenance.parquet | Связи readers с каноническими сущностями; person_observations переименовано в observations |
| errors.parquet | Журнал ошибок исходных readers, не смешанный с ошибками T12 |
| normalization_errors.parquet | Причины неверных значений, несовместимых типов и связей |
| transformation_log.parquet | rule_id, версия, число принятых затронутых строк, исключения, примеры до/после |
| duplicate_reads.parquet | Ключи повторно прочитанных записей и число удалённых копий |
| canonical_report.json | Входные SHA-256, версии, состав источников, балансы, ограничения, время |
| canonical_summary.txt | Краткий итог |
| canonical_manifest.json | SHA-256 завершённых файлов T12; публикуется последним |

Схемы — `normalize/canonical.py::SCHEMAS`. Это **canonical_contract_version=1.0**,
отдельный контракт от неизменённых схем readers T04. Совместимые поля readers
сохранены; добавлены сравнимые значения и происхождение. Поля value/kind и другие
неключевые поля могут стать null при несовместимом типе — целый профиль при этом
не удаляется. Обязательные идентичности source_id/source_record_id/locator/PK и
observation_id ребёнка должны быть непустыми строками: иначе сборка прерывается,
поскольку нельзя выдумать правильную связь.

Каждая строка имеет input_schema_sha256 (описание схемы в отчёте), normalization_version, normalization_rules_json,
source_values_json и normalization_status. Корректные исходные `*_raw`, raw_json,
raw_line сохраняются без изменения. Остальные исходные поля также сохраняются,
кроме описанных проверок дат/типов и алиаса provenance. Если базовое поле изменено,
его оригинал находится в source_values_json. Неизвестные входные поля сохранены
там как `extra:<имя>`. Несовместимый bytes/date/datetime кодируется явным JSON-
объектом с типом; нечисловые NaN/Infinity — nonfinite_float. Это восстановление
значений, не обещание байтовой идентичности исходного Parquet-контейнера.

T13 получает стабильные observation_id/identifier_id/travel_id, представления
для сравнения, тип свидетельства и все исходные ссылки. Документ/карта сами по
себе не назначают person_id; содержательные дубли поездок между источниками
сохраняются. Наименование event_kind и STATUS не доказывает фактическую посадку.

## Правила

| rule_id | Правило и ограничения |
|---|---|
| name.nfkc_casefold_space | name_comparison: NFKC, casefold, схлопывание Unicode-пробелов; исходное имя не заменяется |
| name.ru_ascii_v1 | name_latin_comparison: явная таблица русских букв и латинские диакритики; вспомогательный ключ, не доказательство личности |
| date.source_format | Полная ISO-дата/время или явно заданный формат источника; никакого обмена дня и месяца ради успешного parse |
| date.precision | Сохраняет date/minute/second/invalid/null; дата без часов не получает полночь |
| date.manual_precision | Точность времени после подтверждённого ручного исправления ISO-значения |
| identifier.type_preserving | Нормализация только по kind и конфигурации; значимые буквы/нули/внутренние пробелы сохраняются |
| identifier.programme_context | Отдельное представление программы через NFKC/casefold/пробелы |
| identifier.namespace | Контекст документа/билета или программа карты; unknown_programme не даёт общего ключа |
| identifier.namespace_value_key | JSON-ключ namespace + нормализованное значение; без смешения программ карт |
| string.nfkc_outer_space | Отдельные flight_number_normalized, ticket_number_normalized, booking_code_normalized; исходные поля остаются |
| schedule.validate_period | valid_from/valid_to должны быть полными ISO date и не перевёрнутыми; неизвестный период остаётся неизвестным |
| provenance.canonical_alias | person_observations → observations; оригинал имени таблицы восстанавливается из source_values_json |
| type.incompatible | Неключевое значение несовместимого типа → null и явная ошибка; числовой документ не превращается в восстановленный номер |
| relation.foreign_key | Отсутствующая цель/неверный владелец карты/ошибка provenance фиксируются отдельно, исходная строка не исчезает |

Общие пустые значения из конфигурации: пустая строка, None, Not presented, N/A
после внешних пробелов и casefold. Число/строка 0 не означает неизвестность.
Эти правила применяются к очищаемым представлениям и датам; неописанные статусы,
тарифы, пол и другие исходные атрибуты не переинтерпретируются.

Для BoardingData birth_date строго MM/DD/YYYY. Для других источников допустимые
числовые форматы явно перечислены в normalization.yaml (включая DD/MM/YYYY там,
где это подтверждено контрактом reader). Для поездок BoardingData разрешён ISO.
Год/месяц/день и часы/минуты должны присутствовать полностью в формате;
конфигурация не может подставить 1900 год или нулевые часы через strptime.
Неверная или частичная дата, противоречие raw и результата reader, конфликт
точности дают null и причину в normalization_errors. raw сохраняется.

Русская транслитерация — локальное правило ru_ascii_v1, а не заявление о полном
соответствии ГОСТ/ISO: ё→yo, ж→zh, й→y, х→kh, ц→ts, ч→ch, ш→sh, щ→shch,
ы→y, э→e, ю→yu, я→ya, ъ/ь удаляются только в сравнительном представлении.
Другие алфавиты остаются Unicode, без выдуманных соответствий. Совпадение
транслитерации может только ограничивать поиск кандидатов T13.

## Идентификаторы и ручные исправления

Документы, билеты и карты остаются строками. `000123` не становится `123`.
Внутренние пробелы/пунктуация/буквы по умолчанию не удаляются. Case по умолчанию
preserve; настройки задаются отдельно для каждого kind. Числовой вход в value
получает null + incompatible_type, оригинальное число сохраняется; недостающие
нули не угадываются.

Карта сравнима только внутри программы: namespace вида
`["loyalty_card","programme","fb"]`. Без программы identifier_match_key=null.
Тип документа/эмитент и контекст билета в контракте readers не подтверждены,
поэтому их default namespace ограничен source_id. Для межисточникового ключа
требуется подтверждённый namespace_overrides с source_id/kind/namespace/reason/
evidence. Это ограничение явно передаётся T13; нельзя объявить все документы
одинаковым типом или все билеты одного контекста из сходства цифр.

manual_corrections по умолчанию пусты. Нужны rule_id, source_id, entity_table,
entity_id, field, original, replacement, reason и evidence. Менять можно только
разрешённые очищенные поля; PK, ссылки и raw напрямую менять нельзя. original
должен совпасть; невалидные ISO-замены и неиспользованные правила прерывают
сборку. Конфигурация с исправлениями коммитится; её SHA-256 хранится в отчёте.
В каждой затронутой строке есть rule_id, а в журнале — пример до/после.
При исправлении имени обновляется зависимая транслитерация, при исправлении
карты — контекстный ключ, при исправлении времени — точность.

## Повторное чтение, баланс и ошибки

Дедупликация означает **точно повторённый объект с тем же исходным PK и теми же
значениями**, включая исходный payload и типы/схему входа. Для provenance ключ составной:
entity_table + entity_id + source_record_id. Конфликтующие копии одного ключа
прерывают сборку; не выбирается случайный вариант. Другая исходная запись с
другим locator/версией получает другой ID и остаётся отдельным свидетельством,
даже если рейс, документ и имя выглядят одинаково. Это не дедупликация событий T13.

Для каждой пары source_id/сущность проверяется баланс:
input_rows = output_rows + duplicates_removed. Счётчик ошибок не вычитается
из числа профилей/поездок: одна строка может иметь несколько ошибок полей.
Один профиль может породить несколько карт/поездок — равенства этих таблиц нет.
В source_reports сохранены исходные отчёты поставщиков, включая incomplete PDF;
сборка T12 не объявляет их автоматически принятыми. errors.parquet сохраняет
журнал readers, normalization_errors — только проблемы нормализации/связей.
normalization_status относится к полям строки; межтабличные проблемы читаются
дополнительно из normalization_errors и общего отчёта.

## Совместимость и безопасная публикация

T12 пишет только свои файлы и использует отдельную системную блокировку
`.canonical.lock`. Итоговые файлы T11 (travel_geography, schedule_links и другие)
и readers/checkpoint не заменяются. Текущий процесс T11 можно оставить работать;
обновление кода и следующий запуск выполнять после его завершения.
Manifest T12 публикуется последним; потребитель сверяет SHA-256. Несколько файлов
не образуют атомарный снимок для параллельного reader, не читать их во время
публикации T12. Ctrl+C освобождает системную блокировку; файл lock остаётся и
не запрещает новый запуск. Прогресс T12 после прерывания не восстанавливается.

При обычной ошибке публикация откатывает заменённые файлы. Ошибка/прерывание
сохраняет canonical_last_failure.json отдельно от прежнего успешного manifest.
При аварийном завершении во время нескольких rename нужно сверить manifest,
сохранить оставшийся временный .canonical-* с backup и восстановить завершённый
набор. Не удалять активный lock или резервные каталоги вслепую.

Передача T11 (последние исправления включены в проект):

```powershell
python scripts/run_t11.py --input data/processed --schedules data/interim/real/timetable_pdf/schedules.parquet
```

T11 использует flight_number_normalized, если он есть; исходный номер сохраняется.
Несовместимый тип исходной точки не трактуется как пропущенный аэропорт, который
можно вывести из расписания. Неверное исходное время также не заполняется как
отсутствующее. Для автоматического вывода нужен исходный отчёт покрытия PDF;
без него каноническое расписание используется только в ограниченной роли.

## Воспроизведение проверок

```powershell
python -m pytest -q
python -m pytest -q tests/test_normalize.py
python scripts/run_t12.py --input examples/interim --output data/processed/demo_t12 --require-all
python scripts/benchmark_t12.py --output data/benchmark/t12
```

Результаты — docs/validation/t12_validation.json и t12_benchmark.json.
Измерение 160000 искусственных входных строк не является прогоном полного
реального набора. Реальные исходные Parquet и независимый reviewer нужны для
окончательной приёмки. Техническая реализация не заменяет это подтверждение.
