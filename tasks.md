## 1. Конечная цель

Сделать работающий исследовательский продукт, который из разрозненных файлов собирает историю поездок пассажира, находит необычные сочетания маршрутов и повторных совместных перелётов, объясняет причины высокого места в рейтинге и позволяет проверить их по исходным данным.

На выходе пользователь открывает программу, видит рейтинг интересных для изучения историй, выбирает человека и получает досье: поездки по времени, доступные маршруты, повторных спутников, признаки необычности, качество сведений и ссылки на записи, из которых всё это получилось. Можно сравнить результат понятных правил с моделью машинного обучения, выгрузить таблицу и повторить расчёт.

**Три цели, которые показываем на защите:**

1. Объединить и очистить все семь логических источников, связать записи об одних людях и поездках, сохранить происхождение результата и все существенные преобразования.
2. Построить и проверить объяснимый рейтинг аномалий: правила + Isolation Forest + признаки графа совместных перелётов. Показать, что добавляет каждая часть, где она ошибается и насколько устойчив результат.
3. Передать воспроизводимый продукт: код, обработанные данные, артефакт модели, интерфейс, технический отчёт и материалы защиты по лекции.

**Аномалия** означает необычность относительно выбранных данных. При отсутствии достоверных меток «шпион / не шпион» мы не обучаем классификатор на придуманных ответах. Балл не является вероятностью шпионажа. Полезный результат — конкретные проверяемые паттерны и корректный разбор их возможных объяснений.

## 5. Как делаем и проверяем модель

### Последовательность

1. Readers извлекают исходные наблюдения и сохраняют их происхождение.
2. Общие правила чистят значения; география связывает места со справочником, расписание используется только при совместимости периода и маршрута.
3. Сопоставление создаёт person_id и недублированные segment_id. Спорные связи сохраняются отдельно.
4. Из историй считаются числовые признаки; граф добавляет повторные совместные события с проверкой случайного фона.
5. Правила дают объяснимый baseline. Isolation Forest ищет необычные сочетания признаков. Сохраняются отдельные и комбинированный рейтинги.
6. До интерфейса проверяются сценарии, независимый ручной аудит, чувствительность к настройкам и вклад отдельных групп признаков.
7. Сайт читает принятый результат и раскрывает объяснения, маршруты, связи и источники.

### Что делает проект содержательно сложным

| Часть | Почему это интересная инженерная/аналитическая задача | Что демонстрируем |
|---|---|---|
| Сопоставление людей | Разные имена, программы и документы, неполные записи, тёзки, транзитивные конфликты | Принятая связь и спорная связь с доказательствами |
| Последовательности поездок | Нельзя путать дату/час/пояс и приписывать неизвестный origin | Реальный восстановленный фрагмент и явно неизвестные участки |
| Граф | Повторные встречи нужно отличать от популярных рейсов и повторных копий билета | Ребро → события → источники; сравнение со случайным фоном |
| Модель аномалий | Нет готовой целевой разметки; нужно избежать рейтинга ошибок данных | Правила против IF, случаи расхождения, ограничения |
| Проверка | Красивый top-10 легко получить, его достоверность сложнее обосновать | Слепой аудит, стабильность top-K, результат без графовых признаков |
| Воспроизводимость | Много источников и этапов могут незаметно смешать версии | Один run_id, параметры, контрольные суммы и повторный запуск |

Основной учебный рейтинг T17: число независимых сработавших групп по убыванию,
затем балл правил и стабильный ID. Для будущего учебного сравнения T19 остаётся
отдельный эксперимент 50% процентиля правил + 50% процентиля IF с одинаковыми
midrank-процентилями для равных значений. Его веса — проверяемая гипотеза;
он не подменяет основной топ и не добавляет IF как голос критерия. Выводы
сравнения и чувствительность порогов проверяются в T20.

Результат проверки включает реальные количества и состав выборки. Разметка «интересно проверить» не становится истинной меткой «шпион». Синтетические сценарии проверяют реализацию, а не доказывают эффективность на неизвестных реальных случаях. Если когда-нибудь понадобится прогноз будущих поездок, для него требуется отдельное временное разделение и исключение будущих данных из обучения/признаков.

### Минимальный стек

Python 3.12; `uv` для закреплённого окружения; PyArrow/Parquet для таблиц; DuckDB для запросов; библиотеки потокового чтения и разбора файлов; scikit-learn для Isolation Forest; NetworkX либо собственные табличные операции для небольших графов; pytest/Ruff для содержательных локальных проверок. После T21 — Streamlit и Plotly, затем Docker и GitHub Actions. Точные версии закрепляются в T04 и проверяются при установке; «последняя версия» не является требованием.

Отдельные API-сервер, React, серверная БД, Kubernetes, обучение глубокой нейросети и чат-бот в план не входят. Срок расходуется на качественный аналитический результат. Нейросети помогают писать код и разбираться с форматом; смысл полей, результаты экспериментов и выводы команда проверяет сама.

### Команды, которые должны появиться

Это целевой интерфейс будущей программы, а не команды, уже работающие в исходной ветке. Конкретные параметры фиксирует T04, сохраняя смысл операций.

```bash
uv sync --frozen
uv run python -m yoyoflot inventory --config configs/sources.yaml
uv run python -m yoyoflot ingest --source timetable_pdf --config configs/sources.yaml
uv run python -m yoyoflot run --config configs/sources.yaml --until build
uv run python -m yoyoflot run --config configs/sources.yaml --output artifacts/run-20261016
uv run python -m yoyoflot evaluate --product artifacts/run-20261016
uv run streamlit run app/main.py -- --product artifacts/run-20261016
```

`--until build` нужен для принятого ядра данных 15 октября. Полный `run` с моделью и проверкой закрывается в T21 после интеграции T19/T20. Один выбранный run_id далее указывается в отчёте, интерфейсе и пакете сдачи.

## 6. Правила работы с пулом и критерий «готово»

У каждого одновременно одна основная задача и небольшое ревью. Ветка задачи называется, например, `yan/T13-entity-resolution`; перед началом проверить существующие ветки товарищей и переиспользовать их результат. Ветка интеграции выбирается командой в T04; в репозитории есть `develop`, но старый план не даёт права автоматически переносить в него чужие изменения.

Утром — 10 минут: что беру, что передаю, где блокер. Вечером — короткий показ результата и обновление статуса. Если за 2 часа неясно, как разобрать формат или проверить гипотезу, показать минимальный проблемный пример товарищу. Срыв ранней передачи сообщается сразу, а не в момент финального дедлайна.

**Задача закрывается, когда:**

- Получен результат из карточки, а не только написан код.
- Пройдены содержательные проверки автора и отдельное ревью указанного товарища.
- Все строки/страницы/книги источника учтены; исключения видны и объяснены.
- Реальный расчёт воспроизводится командой; нужные конфигурации и версии зафиксированы.
- Обновлены описание источника/метода и журнал преобразований; будущему автору отчёта не нужно догадываться, что сделали.
- Потребителю переданы формат, версия результата и известные ограничения.
- Статус в `tasks.md` и карточке совпадает; указан PR/commit или другой проверяемый результат.

Тесты здесь защищают смысл данных: тёзки, ведущие нули, дубли, полуночные рейсы, пропуски и реальный расчёт балла. Для перестановки заголовка Markdown или цвета кнопки отдельный набор тестов не нужен.

### Работа с нейросетями

В запрос передаём свою карточку, контракт, связанные файлы и маленький искусственный пример. Сначала просим реализацию текущего шага, затем сами проверяем вход/выход и объясняем товарищу алгоритм. Большая генерация «сделай весь проект» без проверки легко создаст разные схемы и вымышленные поля. Каждый участник отвечает за принятый код и должен объяснить его на защите.

## 9. Короткий словарь

| Термин | Простое объяснение |
|---|---|
| Reader / парсер | Код, который читает один исходный формат и выдаёт общие таблицы |
| ETL / конвейер | Последовательность извлечения, преобразования и сохранения данных |
| Каноническая таблица | Общий договорённый формат, к которому приведены разные источники |
| Entity resolution | Решение, какие записи относятся к одному реальному объекту |
| Blocking | Ограничение сравнения похожими группами кандидатов вместо всех пар |
| Provenance / lineage | Происхождение значения: из какой записи оно взято и каким правилом получено |
| Feature / признак | Вычисленная числовая характеристика истории пассажира |
| Baseline | Простое базовое решение, с которым сравнивается сложное |
| Unsupervised / без учителя | Алгоритм работает без готовых правильных классов объектов |
| Isolation Forest | Алгоритм поиска необычных сочетаний признаков случайными разбиениями |
| Граф | Вершины — объекты, рёбра — отношения между ними; у нас люди и совместные события |
| Перцентиль | Положение значения среди опорных значений; не вероятность истинности гипотезы |
| Top-K | Первые K объектов отсортированного рейтинга |
| Jaccard | Доля пересечения двух списков относительно их объединения |
| Ablation | Повторный расчёт без части признаков, чтобы проверить её пользу |
| Seed | Начальное число генератора случайности для повторяемости эксперимента |
| Fixture | Маленький заранее известный пример входа для проверки кода |
| Snapshot / снимок | Завершённая неизменяемая версия данных и модели одного запуска |
| Parquet | Компактный табличный формат, удобный для чтения выбранных столбцов |
| DuckDB | Локальный движок SQL-запросов к таблицам; отдельный сервер не нужен |
| CLI | Запуск программы командами из терминала |
| CI | Автоматические проверки кода при изменении репозитория |
| DoD / критерии готовности | Проверяемые условия, после которых задача действительно завершена |
