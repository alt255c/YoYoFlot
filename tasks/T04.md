## Зачем нужна задача

Создать минимальную общую основу, чтобы семь парсеров выдавали совместимые данные и команда могла работать параллельно. Это часть модели и обработки данных; веб, Docker и CI здесь не разрабатываются.

## С какими файлами работаем

- `pyproject.toml`, `uv.lock`, `.gitignore` — окружение и зависимости.
- `src/yoyoflot/__init__.py`, `__main__.py`, `cli.py`, `config.py` — пакет и команды.
- `src/yoyoflot/contracts.py`, `io.py`, `provenance.py` — схемы таблиц, порционная запись и происхождение данных.
- `docs/data_contract.md` и `docs/data_dictionary.md` — договорённость о форматах.
- `tests/test_contracts.py`, `tests/conftest.py`, `tests/fixtures/expected.json` — общие проверки.

Пути относятся к целевой структуре репозитория; отсутствующий модуль создаётся в этой задаче. Общие схемы и определения читаем в `docs/data_contract.md` и `docs/data_dictionary.md`.

## Что сделать по шагам

1. Зафиксировать Python 3.12 и зависимости в uv.lock. Основа: PyArrow/Parquet, DuckDB, scikit-learn, библиотека чтения JSON потоком, XML, YAML, XLSX и PDF; точные версии выбираются после проверки установки. Streamlit пока только запланирован.
2. Сделать пакет, запускаемый как `uv run python -m yoyoflot`. Задать команды inventory, ingest, build, features, train, evaluate, run, export. Нереализованные команды явно сообщают об этом и завершаются с ненулевым кодом.
3. Описать общие таблицы наблюдений о людях, идентификаторов, наблюдений о поездках и расписания. Для каждого поля определить тип, смысл null, уникальность и связь с другими таблицами.
4. Зафиксировать интерфейс reader: получает путь/источник, выдаёт порции таблиц с известной схемой и сведения об ошибках. Парсеры не объединяют пассажиров самостоятельно и не присваивают итоговый балл.
5. У каждой исходной записи должны быть source_id, source_record_id и locator: строка, XML-путь, ключ профиля, книга/лист/строка или страница PDF. Общий provenance связывает преобразованный объект с этими ссылками.
6. Документы, билеты, номера карт и внешние ID хранить строками. Для времени отдельно хранить локальное значение, известный часовой пояс и точность; date-only не превращать в полночь UTC.
7. Организовать запись небольшими порциями. Если таблица пуста, создать корректный пустой результат по схеме. Нельзя возвращать успех после исключения и выдавать недописанный файл за готовый.
8. Создать один искусственный сквозной пример, на котором автор каждого reader проверяет контракт. Внутренние идентификаторы детерминированы по версии входа и locator; добавление другой строки не перенумеровывает весь набор.
9. Сделать общий шаблон заметок: вход → изменение → причина → количество строк → исключения → выход. Заметки автора остаются рядом с описанием источника.
10. Передать всем короткий пример reader и согласовать контракт к 10 октября 14:00. После этого изменение схемы сопровождается версией и обновлением потребителей.

## Пример или важная проверка

Форма интерфейса: `read(path, source_id) -> Iterator[TableBatch]`. `TableBatch` содержит `table_name`, записи согласованной схемы и счётчики. Это предложение интерфейса; точное определение фиксируется здесь один раз, а не придумывается отдельно каждым автором.
