## Зачем нужна задача

Убедиться, что итоговые данные не потеряны, не размножены ошибочным join и не лишились происхождения. Этот контроль нужен до оценки необычности пассажиров.

**Параллельная работа:** исследование, искусственные примеры и код по контракту T04 можно готовить до закрытия всех зависимостей. Финальный результат принимается на реальных выходах завершённых поставщиков.

## С какими файлами работаем

- `src/yoyoflot/quality.py` — проверки таблиц, связей и количеств.
- `tests/test_quality.py` — реальные классы возможных ошибок.
- `data/processed/lineage.parquet` — связи результатов с источниками и правилами.
- `reports/quality.json` и `reports/quality.md` — измеренный результат проверок.
- `docs/validation.md` — протокол и выявленные дефекты.

Пути относятся к целевой структуре репозитория; отсутствующий модуль создаётся в этой задаче. Общие схемы и определения читаем в `docs/data_contract.md` и `docs/data_dictionary.md`.

## Что сделать по шагам

1. Проверить обязательные поля, типы, уникальность ключей и отсутствие «висячих» ссылок. Каждая поездка ссылается на существующий профиль или имеет явный статус неопределённой идентичности.
2. Свести баланс по этапам: прочитано, принято, развернуто из вложений, объединено как дубль, исключено и оставлено на разбор. Для каждого расхождения указать конкретное правило.
3. Проверить, что число поездок не выросло при объединении документов/карт и что общий ZIP не дал вторую копию всего набора.
4. Построить таблицу покрытия по источникам: документы, карты, дата, две точки маршрута, время, уверенная идентичность. Она нужна для выбора допустимых признаков.
5. Проверить происхождение каждого объекта, а не только нескольких примеров: у всех используемых person_id/segment_id есть путь к source_id + locator. Для выведенного поля есть rule_id.
6. Сделать независимый ручной обход минимум 30 объектов из разных источников/статусов, включая спорные связи и расписание. Сева выбирает примеры сама, а не только удачные случаи автора.
7. Разделить блокеры и ограничения. Потеря источника, неверный join или недоступное происхождение — блокер. Честно сохранённая неизвестная дата — ограничение, которое отключает конкретный расчёт.
8. Сохранить JSON для интерфейса и Markdown для команды. Передать дефекты владельцу соответствующего reader/правила; после исправления повторить только затронутую проверку и финальный баланс.

## Ожидаемый результат

- Единый отчёт качества и проверенная таблица происхождения.
- Ясно, какие данные допускаются в модель и граф.

## Критерии готовности

- [ ] Нет неучтённых входных файлов и необъяснённых потерь строк.
- [ ] Все ключевые связи проходят проверки целостности.
- [ ] Каждый используемый в модели объект имеет происхождение.
- [ ] Неразрешённые проблемы перечислены вместе с тем, какие признаки они ограничивают.

## Как закрыть карточку

Ответственный прикладывает результат, команду проверки и известные ограничения. Проверяющий подтверждает критерии выше. После приёмки обновляются статус здесь и строка в `tasks.md`; если изменён общий формат, обновляются контракт и его потребители.
